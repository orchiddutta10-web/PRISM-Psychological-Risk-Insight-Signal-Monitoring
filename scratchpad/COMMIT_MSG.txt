fix(chatbot): add NOVA-compat shim routes so the dashboard chatbot works

The dashboard's `/chatbot` page calls four endpoints that don't exist
on the running API:

  - POST /api/v1/companion/rag/search      → 404
  - GET  /api/v1/companion/mood/timeline   → 404
  - POST /api/v1/nova/chat                 → 404
  - GET  /api/v1/nova/conversations/{id}   → 404

The first console error the user saw was the RAG search 404. These
endpoints were removed during the audit cleanup (the original NOVA
service / behaviour / ml routes were unimportable dead code).

## Fix

Added 4 compatibility shim routes to `services/api/app/routes/companion.py`:

- `POST /api/v1/companion/rag/search` — semantic-search the medical KB
  via the existing `medical_rag.search()` helper. Returns `{results_count,
  results: [{id, role, message, sentiment, timestamp}], method}`.
  Returns empty `results` if the KB is unconfigured rather than 503.

- `GET /api/v1/companion/mood/timeline?days=N` — returns an empty daily
  timeline. Per-message sentiment tagging isn't implemented yet so this
  returns a single neutral-day entry; the dashboard renders an empty
  state instead of throwing.

- `POST /api/v1/nova/chat` — writes both user + assistant turns to
  `ChatMessage` (keyed by guardian_id, the current schema). Calls
  `handle_companion_message()` so the crisis-keyword gate still
  triggers. Returns `{conversation_id, message, crisis_flag}`. The
  crisis path was crashing because `handle_companion_message` assumed
  `comp_session` was non-null; now it falls back to deriving the
  persona from the synthetic id when no real session exists.

- `GET /api/v1/nova/conversations/{conversation_id}` — returns the
  guardian's full `ChatMessage` history as the conversation thread.
  Returns empty `messages` (instead of 404) so the dashboard's
  conversation-restore flow doesn't bail on first load.

## Why NOVA writes to ChatMessage, not CompanionSession

The current `CompanionSession.subject_id` is a non-nullable FK to
`child_devices` and the schema never had a `session_id` column on
`ChatMessage` (the old design assumed `ChatMessage.session_id` linked
back to `CompanionSession`). The NOVA-compat shim uses a synthetic
id of the form `<guardian_id>-<persona_id>` so the companion engine
can still apply persona-specific responses, and persists turns in the
table the rest of the system actually reads (`ChatMessage`).

## Verification

Live smoke test (guardian = chatbot-test@example.com):

  - GET  /api/v1/companion/personas        → 200 (6 personas)
  - POST /api/v1/companion/rag/search      → 200 (2 KB chunks for "fever")
  - GET  /api/v1/companion/mood/timeline   → 200 (empty timeline)
  - POST /api/v1/nova/chat (regular msg)   → 200, crisis_flag=false
  - POST /api/v1/nova/chat (crisis msg)    → 200, crisis_flag=true,
                                              returns CRISIS_RESPONSE

84/84 API tests still pass. 0 TypeScript errors.
